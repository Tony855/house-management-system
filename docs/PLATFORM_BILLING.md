# Platform Super Admin & Billing

## Product authority
The Super Admin is the platform owner/operator control plane, not a fourth tenant business account. It has its own identity store, login audience, MFA policy and platform API. It owns the Rental, Hotel and Property product catalog; plans, pricing, billing intervals, trials, quotas and entitlements; tenant subscriptions; platform invoices; payment attempts, verified webhooks, refunds; platform revenue ledger, reconciliation, delinquency policy and billing audit history; tenant lifecycle and service-health aggregates.

It does NOT own tenant users, customers, guests, owners, employee records, operational bills, rent collections, hotel orders, tenant payment details or tenant files. Those remain in each tenant's isolated database.

## Billing lifecycle
1. Publish a product-specific plan with currency and interval. Subscription price is snapshotted; editing a plan never silently reprices existing subscriptions.
2. Create a subscription with explicit trial, period, quantity, price and currency.
3. Generate one invoice per subscription and billing period. Use idempotency keys and unique period constraints so retries cannot duplicate invoices.
4. Issue immutable invoice line snapshots and append a ledger entry. Corrections use credit/debit adjustments or void-and-reissue with audit.
5. Payment providers are adapters. Verify webhook signature and timestamp against the raw request body before accepting events; persist provider event ID under a unique key before side effects. Replays are no-ops.
6. Payment success is recorded transactionally with invoice settlement and ledger entry. Partial payments are multiple transactions; browser redirects are never proof of payment.
7. Refunds require a reason, authorized platform admin, idempotency key and captured-balance check. Refunds append ledger entries; original payments are never deleted.
8. Delinquency uses a configurable grace period and explicit lifecycle state machine. Failed billing must not run destructive tenant DB actions.

## Money and currency
- Store integer minor units (USD cents, KHR riel, KWD fils); use the ISO 4217 currency exponent.
- Every invoice, payment and refund carries an explicit ISO currency. Never mix currencies in aggregates.
- FX, if added, must persist source/target currency, exact rate, source, quote timestamp and rounded result.
- Tax, discount, proration and rounding policies are explicit and snapshotted on each invoice.

## Access and security
- Only platform-admin sessions with the platform audience can access billing APIs.
- Product tenant APIs cannot read platform invoices, payment methods, billing accounts or ledger rows.
- Provider secrets live in a secret manager; DB stores references only. Never log card data, secrets or raw webhook payloads.
- Verify webhook signatures over raw bodies and enforce replay windows and unique provider event IDs.
- Ledger and audit tables are append-only at the application/DB-grant layer. Manual adjustments require reason and before/after audit.
- Financial exports are generated by Platform API and permission-checked.

## Legacy migration
Existing usage_fee_config, orgs.fee_* and usage_fee_payments are legacy fields in the shared house_sys database. Do not drop or rewrite them during this phase. A later migration must map every existing org to one platform tenant UUID; snapshot fee cycle, price, currency, start and due dates into subscriptions; import historical payments with stable source references; reconcile totals and balances per org; shadow-compare the new billing read model before cutover; and provide dry-run, rollback and per-org cutover. No destructive migration and no unreviewed dual-write.

## Delivery status
The SQL migration and pure domain validation helpers are foundations only. They are not wired to a running Platform API, payment provider, super-admin frontend, scheduled invoice issuer or production MariaDB migration runner. Do not advertise live online billing until those integrations and end-to-end tests are complete.
